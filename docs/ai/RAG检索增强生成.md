大模型什么都懂一点，但不知道你的私有文档、你的业务数据、昨天刚更新的产品手册。RAG（Retrieval-Augmented Generation，检索增强生成）就是解决这个问题的主流方案——先检索相关资料，再让模型基于资料回答。

## 为什么需要 RAG

微调（Fine-tuning）也能让模型学习新知识，但：

- 微调成本高，每次更新都要重新训练
- 微调是"把知识压进参数"，无法给出来源，也无法精确更新某一条
- 模型仍然会产生幻觉

RAG 的优势：

- 知识在外部数据库，随时更新，成本极低
- 可以给出引用来源，可追溯、可验证
- 不需要训练模型，接上就行

代价是引入了一整套检索系统的复杂度。

## RAG 的完整流程

```
文档 → 切分 → 向量化 → 存入向量库
                              ↓
用户问题 → 向量化 → 相似度检索 → 召回相关片段
                              ↓
        [问题 + 检索片段] → 大模型 → 答案（带引用）
```

分成两条线：**离线建库**和**在线问答**。

## 第一步：文档切分（Chunking）

这是最容易被低估的环节。切分质量直接决定检索效果。

**固定长度切分**最简单，但会切断语义——一句话被切成两半，两个片段都不完整。

**按语义切分**更好：按段落、标题层级切，每个 chunk 保持语义完整。

实用参数：

- chunk 大小：300~800 token（中文约 500~1000 字）
- overlap：相邻 chunk 重叠 10~20%，避免边界信息丢失
- 保留元数据：每个 chunk 带上来源文件、标题、章节路径，用于最终引用

```ts
const splitter = new RecursiveCharacterTextSplitter({
  chunkSize: 600,
  chunkOverlap: 100,
  separators: ['\n\n', '\n', '。', '，']
})
```

## 第二步：向量化（Embedding）

把每个 chunk 转成向量。选 embedding 模型要注意：

- **中文支持**：优先选对中文优化的模型（如 text-embedding-v3、bge-m3）
- **维度与成本**：维度越高表达力越强，但存储和检索成本也高
- **一致性**：建库和查询必须用同一个模型的同一个版本，换模型要全量重建

## 第三步：向量检索

基础做法是余弦相似度检索 top-k：

```ts
const results = await vectorStore.similaritySearch(query, 5)
```

但生产环境通常需要**混合检索**：

- **向量检索**：擅长语义相似（"怎么提升性能"能匹配到"优化响应时间"）
- **关键词检索**（BM25）：擅长精确匹配（产品型号、错误代码、专有名词）

两者结合（Hybrid Search）再做过重排（Rerank），效果比单纯向量检索好很多。

```ts
// 1. 混合召回
const candidates = await hybridSearch(query, { vectorTopK: 20, keywordTopK: 20 })
// 2. Rerank 模型精排
const ranked = await reranker.rerank(query, candidates, { topK: 5 })
```

## 第四步：构造 Prompt

把检索到的片段和问题一起给模型，**明确要求基于材料回答**：

```
请严格根据以下参考资料回答问题。如果资料中没有相关信息，回答"资料中未提及"，不要自行编造。

【参考资料】
{context}

【问题】
{question}

【要求】
- 答案中标明引用来源（如 [资料1]）
- 不要使用资料之外的知识
```

关键两点：**要求基于资料**（抑制幻觉）和**允许说不知道**（避免硬编）。

## 常见坑

**检索不到相关内容**：
- chunk 粒度不合适（太大稀释语义，太小丢失上下文）
- embedding 模型不适配中文
- 用户问题和文档表述差异大 → 用 Query Rewriting 改写问题，或用多路召回

**检索到了但答不好**：
- 召回的片段太多，超出上下文窗口 → 控制 top-k
- 无关片段干扰 → 加 Rerank
- 关键信息在 chunk 边界被切断 → 调 overlap

**更新不及时**：
- 文档变更后要重新切分、向量化、更新索引。增量更新要注意删除旧版本，否则检索到过期内容。

## 评估

RAG 系统必须建评估集，否则优化全凭感觉：

- **检索层**：召回率（相关文档有没有被找到）、精确率（找到的是不是相关）
- **生成层**：答案正确性、是否忠于资料（无幻觉）、引用是否准确

准备 50~100 个"问题 + 标准答案 + 应引用的文档"的测试集，每次改动跑一遍，用数据说话。

## 小结

RAG 不复杂，难在细节：切分策略、embedding 选型、混合检索、Prompt 约束、评估体系。这五个环节哪个掉链子，最终效果都会打折。

从最简单版本开始（固定切分 + 向量检索 + 基础 Prompt），跑通后再逐个环节优化——这是最稳的推进路径。
