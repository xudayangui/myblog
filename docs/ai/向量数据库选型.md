做 RAG 绕不开向量数据库。市面上选择很多——Pinecone、Milvus、Qdrant、Weaviate、Chroma，甚至 PostgreSQL 加个插件也能干。这篇讲怎么选，以及实际用起来会踩的坑。

## 先问自己三个问题

**1. 数据规模多大？**

- 几万条以下：内存里算就够了（Faiss、Chroma），甚至 PostgreSQL 的 pgvector 都绰绰有余
- 百万到千万：需要专业的向量库（Qdrant、Milvus）
- 上亿：考虑分布式方案（Milvus 集群、Pinecone）

**2. 要不要托管？**

托管服务（Pinecone、Zilliz Cloud）省运维但按月收费；自建（Qdrant、Milvus）省钱但要自己管扩容、备份、监控。团队小、数据量不大就托管，别把精力花在运维数据库上。

**3. 需要什么额外能力？**

- 元数据过滤（"只在 2025 年的文档里搜"）→ 大部分库都支持
- 混合检索（向量 + 关键词）→ Qdrant、Weaviate、Elasticsearch 支持较好
- 多租户隔离 → 看各库的 collection/namespace 设计

## 主流方案对比

| 方案 | 类型 | 优势 | 适合场景 |
|------|------|------|---------|
| pgvector | PostgreSQL 插件 | 复用现有 PG，事务一致，运维零成本 | 中小规模，已有 PG 基础设施 |
| Qdrant | 专用向量库 | 轻量、性能强、混合检索好 | 中等规模，自托管 |
| Chroma | 嵌入式 | 极简，几行代码跑起来 | 原型开发、本地测试 |
| Milvus | 分布式 | 支持十亿级，功能全 | 大规模生产环境 |
| Pinecone | 全托管 | 零运维，弹性好 | 不想管基础设施的团队 |

**我的建议**：从 pgvector 或 Chroma 起步。RAG 项目失败的原因 90% 不是向量库性能不够，而是数据质量和检索策略有问题。等真的遇到瓶颈再迁移——向量库之间迁移成本不高，反正 embedding 数据可以重新生成。

## pgvector 实战

如果你已经有 PostgreSQL，这是成本最低的方案：

```sql
-- 启用扩展
CREATE EXTENSION vector;

-- 建表
CREATE TABLE documents (
  id BIGSERIAL PRIMARY KEY,
  content TEXT,
  embedding vector(1536)
);

-- 建索引（余弦距离）
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);

-- 相似度查询
SELECT content, 1 - (embedding <=> $1) AS similarity
FROM documents
ORDER BY embedding <=> $1
LIMIT 5;
```

`<=>` 是余弦距离操作符。HNSW 索引是近似最近邻（ANN）算法，牺牲极小精度换巨大性能提升——百万级数据查询毫秒级返回。

注意 `vector(1536)` 的维度必须和你的 embedding 模型输出一致。换模型要改这一列并重建索引。

## 常见坑

**1. 距离度量选错**

余弦相似度（cosine）适合文本，欧氏距离（L2）适合数值特征，内积（dot）适合归一化向量。文本 embedding 一般选 cosine，选错了检索质量会明显下降。

**2. 忘了元数据过滤**

纯向量检索会返回所有相似内容，包括你不想要的（比如已删除的文档、其他租户的数据）。用元数据过滤缩小范围：

```ts
qdrant.search({
  vector,
  filter: { must: [{ key: 'tenant_id', match: { value: currentTenant } }] },
  limit: 5
})
```

**3. 索引参数调优**

HNSW 的 `m` 和 `ef_construction` 影响召回率和构建速度。默认值通常够用，但数据量大时要在"查询速度"和"召回准确率"之间权衡。用评估集测一下不同参数的召回率，别凭感觉。

**4. 向量维度不一致**

这是最常见的事故：建库时用 768 维模型，查询时换成了 1536 维模型，直接报错。把模型版本和维度写进配置，启动时校验。

**5. 没有考虑更新和删除**

文档更新后要删除旧的向量记录再加新的，只加不删会检索到过期内容。用 `document_id` 作为业务主键，更新时先按它删除。

## 性能判断

不要迷信 benchmark，用自己的数据测：

- **召回率**：已知的"问题-正确文档"对，检索能否找回来
- **延迟**：P50 / P99 查询耗时
- **内存占用**：百万级 1536 维向量约 6GB（float32）

如果召回率低于 90%，先检查 embedding 模型和切分策略，再考虑调索引参数——问题通常出在上游。

## 小结

向量数据库不是 RAG 的瓶颈，检索策略和 embedding 质量才是。选型遵循"够用就好"：

- 原型 → Chroma
- 已有 PG、中小规模 → pgvector
- 中等规模自托管 → Qdrant
- 大规模 → Milvus / 托管服务

先把最简方案跑通，用评估集验证效果，有真实瓶颈了再升级。别在第一步就陷入选型瘫痪。
