React 的状态管理方案层出不穷：Context、Redux、Zustand、Jotai、Recoil……到底该怎么选？这篇文章按场景给出建议。

## 先明确你遇到的问题是哪一种

状态管理其实要解决两类不同的问题：

1. **组件间共享状态**：多个组件需要读写同一份数据
2. **远程数据管理**：从服务端获取、缓存、同步数据

很多方案混淆了这两者。先分清问题，再选工具。

## 场景一：简单的跨组件共享

用 Context + useState 就够：

```javascript
const ThemeContext = createContext()

function App() {
  const [theme, setTheme] = useState('light')
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <Page />
    </ThemeContext.Provider>
  )
}
```

适合主题、语言、用户信息这类变化不频繁的状态。注意：Context 变化会让所有消费组件重渲染，频繁变化的场景要小心。

## 场景二：客户端全局状态

推荐 **Zustand**——轻量、API 简洁、不需要 Provider：

```javascript
import { create } from 'zustand'

const useStore = create((set) => ({
  count: 0,
  increment: () => set(state => ({ count: state.count + 1 })),
  reset: () => set({ count: 0 })
}))

// 组件里按需订阅，只订阅用到的部分
const count = useStore(state => state.count)
```

相比 Redux，Zustand 样板代码少得多，TypeScript 支持也好。

## 场景三：服务端数据

这类问题交给专业工具：**TanStack Query**（原 React Query）或 SWR：

```javascript
const { data, isLoading, error } = useQuery({
  queryKey: ['user', userId],
  queryFn: () => fetchUser(userId),
  staleTime: 5 * 60 * 1000
})
```

它自动处理缓存、重新验证、竞态、分页、乐观更新——这些自己手写极易出错。用了它你会发现，大部分「全局状态」其实是服务端数据的缓存，根本不需要 Redux。

## 什么时候还需要 Redux

- 大型团队需要统一的状态变更规范和强约束
- 有复杂的时间旅行、调试需求（Redux DevTools）
- 遗留项目已经在用，迁移成本大于收益

如果是新项目，多数情况下 Zustand + TanStack Query 的组合更清爽。

## 原子化方案：Jotai

如果喜欢细粒度响应式，Jotai 用「原子」组织状态：

```javascript
const countAtom = atom(0)
const doubleAtom = atom(get => get(countAtom) * 2)

const [count, setCount] = useAtom(countAtom)
```

派生状态自动追踪依赖，适合状态间有复杂计算关系的场景。

## 小结

没有银弹，按需求选：

- 简单共享 → Context
- 客户端全局状态 → Zustand
- 服务端数据 → TanStack Query
- 需要强规范或维护遗留项目 → Redux
- 细粒度派生状态 → Jotai

新项目的默认建议：**TanStack Query 管服务端数据 + Zustand 管客户端状态**，覆盖 90% 的场景。
