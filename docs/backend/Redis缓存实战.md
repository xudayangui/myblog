缓存用得好，QPS 翻十倍；用得不好，Redis 被打穿，数据库跟着一起挂。这篇讲缓存的三类经典问题和对应的工程解法。

## 先分清三个概念

**缓存穿透**：查一个根本不存在的数据。比如用户 ID = -1，缓存里没有，数据库也没有，每次请求都穿透到数据库。黑客拿这个打你，数据库就废了。

**缓存击穿**：一个热点 key 过期的瞬间，大量请求同时发现缓存没了，一起打到数据库。

**缓存雪崩**：大量 key 在同一时刻过期，或 Redis 整个宕机，请求像雪崩一样全涌向数据库。

## 穿透的解法

**方案一：缓存空值**

查不到也往缓存写个空值，设个短 TTL（比如 60 秒）：

```js
const user = await db.find(id)
if (!user) {
  await redis.setex(`user:${id}`, 60, '')
  return null
}
```

简单有效，缺点是会占用一些内存存垃圾 key。

**方案二：布隆过滤器**

在缓存前加一层布隆过滤器，判断 key 是否可能存在。不存在的直接返回，连缓存都不查：

```js
if (!bloom.mightContain(id)) return null
```

适合数据量巨大且恶意请求多的场景。缺点是有误判率（说存在可能不存在，但说不存在一定不存在），且删除元素麻烦。

**实践建议**：先用缓存空值，简单够用；被恶意攻击时再上布隆过滤器。

## 击穿的解法

**方案一：互斥锁**

只让一个请求去查数据库重建缓存，其他请求等着：

```js
async function getData(key) {
  let data = await redis.get(key)
  if (data) return JSON.parse(data)

  const lock = `lock:${key}`
  if (await redis.set(lock, '1', 'NX', 'EX', 10)) {
    try {
      data = await db.query(key)
      await redis.setex(key, 3600, JSON.stringify(data))
      return data
    } finally {
      await redis.del(lock)
    }
  }
  // 没拿到锁，等一会儿重试
  await sleep(100)
  return getData(key)
}
```

注意锁要设过期时间，防止持有者崩了导致死锁。

**方案二：逻辑过期**

不给 key 设物理过期时间，而是在 value 里存一个过期时间戳。发现过期后异步更新，当前请求先返回旧数据：

```js
{ data: {...}, expireAt: 1712345678 }
```

好处是用户永远不等，代价是短时间内可能读到旧数据。适合对一致性要求不高但拒绝延迟的场景（比如首页推荐）。

## 雪崩的解法

**给过期时间加随机值**：

```js
const ttl = 3600 + Math.floor(Math.random() * 600)  // 3600~4200 秒
```

让 key 的过期时间分散开，避免同一时刻集体失效。

**多级缓存**：本地缓存（Caffeine / LRU）+ Redis。Redis 挂了还有本地缓存顶一会儿。

**高可用**：Redis 哨兵或 Cluster，避免单点故障。

**限流降级**：最坏情况下保护数据库，返回默认值或错误页，而不是让数据库被压垮。

## 缓存更新策略

最常用的是 **Cache Aside Pattern**：

- 读：先读缓存，没有读数据库，然后写缓存
- 写：先更新数据库，再删除缓存

注意是**删除**缓存不是更新缓存，因为更新可能产生并发脏数据（两个写操作顺序颠倒）。

"先删缓存再更新数据库"为什么不推荐？因为删完缓存到更新数据库之间，有读请求会把旧数据写回缓存，导致脏数据。虽然概率低（需要恰好在窗口期发生），但"先更新数据库再删缓存"更稳妥。

如果要求强一致，可以用**延迟双删**：

```js
await db.update(data)
await redis.del(key)
await sleep(500)         // 等可能的脏读完成
await redis.del(key)     // 再删一次
```

## 实战清单

- 缓存 key 设计规范：`业务:对象:标识`，如 `user:profile:123`
- 每个 key 都要有 TTL，杜绝永久 key（除非有明确理由）
- 大 key 拆分：单个 value 别超过 10KB，集合类型元素别超过 5000
- 监控命中率：命中率低于 80% 就要看看是不是 key 设计有问题
- 预热：大促前把热点数据提前灌进缓存

## 小结

| 问题 | 特征 | 首选解法 |
|------|------|---------|
| 穿透 | 查不存在的数据 | 缓存空值 + 布隆过滤器 |
| 击穿 | 单个热点 key 过期 | 互斥锁 / 逻辑过期 |
| 雪崩 | 大量 key 同时失效 | 随机 TTL + 多级缓存 |

缓存问题的本质都是"缓存这一层没挡住请求"。理解了请求流向，解法自然就清晰了。
