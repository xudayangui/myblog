线上 Node.js 服务变慢时，从哪里下手？这篇文章按收益从高到低梳理六个优化方向。

## 1. 先测量，别猜

优化前先用工具定位瓶颈：

```javascript
// 用 --inspect 开启调试，配合 Chrome DevTools 的 Performance 面板
node --inspect app.js

// 或用 clinic.js 做火焰图分析
npx clinic doctor -- node app.js
```

没有数据的优化都是瞎猜。重点关注 CPU 火焰图中的宽平原（热点函数）和内存增长曲线。

## 2. 避免阻塞事件循环

Node 是单线程的，一个耗时同步操作会阻塞所有请求：

```javascript
// 错误：同步读取大文件
const data = fs.readFileSync('big.json')

// 正确：异步读取
const data = await fs.promises.readFile('big.json')
```

CPU 密集型任务（如图片处理、大量计算）应该丢到 Worker Thread 或独立进程：

```javascript
const { Worker } = require('worker_threads')
const worker = new Worker('./heavy-task.js')
```

## 3. 数据库连接池

每次请求新建数据库连接是巨大开销。用连接池复用：

```javascript
const pool = new Pool({
  max: 20,  // 根据 CPU 核数和 DB 承载能力调整
  idleTimeoutMillis: 30000
})
```

连接池大小不是越大越好，通常设为 `CPU 核数 * 2 + 有效磁盘数` 是个经验起点。

## 4. 善用缓存

对热点数据加缓存，减少重复计算和 DB 查询：

```javascript
const cache = new Map()

async function getUser(id) {
  if (cache.has(id)) return cache.get(id)
  const user = await db.find(id)
  cache.set(id, user)
  return user
}
```

生产环境建议用 Redis，并注意设置过期时间、缓存穿透和雪崩问题。

## 5. 响应压缩

开启 gzip/brotli 能显著减少传输体积：

```javascript
const compression = require('compression')
app.use(compression())
```

## 6. 集群模式利用多核

单进程只能用一个 CPU 核。用 `cluster` 或 PM2 起多实例：

```bash
pm2 start app.js -i max  # 按 CPU 核数启动实例
```

## 小结

优化顺序建议：**测量定位 → 消除阻塞 → 连接池 → 缓存 → 压缩 → 多进程**。很多时候一个正确的索引或一条缓存命中，比重构一堆代码收益更大。
