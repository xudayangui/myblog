内存泄漏不会让页面立刻崩溃，它像一个慢漏的水龙头——用户开着页面半小时后越来越卡，最终标签页被浏览器干掉。这篇文章讲怎么系统地找到并修掉它。

## 常见的泄漏源头

**1. 未清理的定时器和事件监听**

最常见，也最好查：

```js
// 泄漏
useEffect(() => {
  setInterval(() => setCount(c => c + 1), 1000)
}, [])
```

组件卸载后 interval 还在跑，持有组件引用，整个组件树无法回收。修复永远是"谁申请谁释放"：

```js
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000)
  return () => clearInterval(id)
}, [])
```

**2. 闭包持有大对象**

```js
function setup() {
  const hugeData = new Array(1e6).fill('data')
  document.querySelector('#btn').addEventListener('click', () => {
    console.log('clicked')  // 没用到 hugeData，但它仍被闭包持有
  })
}
```

哪怕闭包里没用到 `hugeData`，某些引擎的作用域优化不彻底时它仍会被保留。解法：把需要的变量显式传进去，或用完置 `null`。

**3. DOM 引用未释放**

```js
const cache = []
function render() {
  const el = document.createElement('div')
  document.body.appendChild(el)
  cache.push(el)  // 移除了 DOM 但数组还引用着
}
```

移除 DOM 节点后，如果 JS 里还留着引用，这块内存不会释放。

**4. 全局变量和缓存**

`window.xxx = ...` 或无限增长的 Map/Set 缓存都是经典泄漏点。缓存一定要有淘汰策略（LRU、TTL）。

## 用 Chrome DevTools 定位

打开 **Memory** 面板，用 **Allocation instrumentation on timeline** 录一段操作：

1. 点开始录制，执行怀疑有泄漏的操作（比如反复打开关闭弹窗）
2. 停止录制，看内存曲线是否呈阶梯状上升且不回落
3. 拍两张 Heap Snapshot，用 **Comparison** 视图对比，按 `# New` 排序

对比视图里重点关注：
- **Detached HTMLDivElement**：已从 DOM 移除但仍被引用的节点，这是最直接的泄漏信号
- 增长最多的对象类型，点进去看 **Retainers**（谁在持有它），一路顺着引用链找到源头

一个实用技巧：拍快照前点几次垃圾桶图标（GC），排除掉本来就该回收的临时对象。

## Performance API 监控

线上环境可以用 `performance.memory`（Chrome 专有）做粗略监控：

```js
setInterval(() => {
  const { usedJSHeapSize, jsHeapSizeLimit } = performance.memory
  const ratio = usedJSHeapSize / jsHeapSizeLimit
  if (ratio > 0.9) console.warn('内存接近上限', ratio)
}, 30000)
```

更严谨的做法是上报 `usedJSHeapSize` 的时间序列，观察长时间趋势是否单调上升。

## WeakMap / WeakSet 的用武之地

当你需要"给对象挂一些元数据，但不想影响它被回收"时，用 WeakMap：

```js
const metadata = new WeakMap()

function attach(el) {
  metadata.set(el, { clickCount: 0 })  // el 被回收时，这条记录自动消失
}
```

WeakMap 的键是弱引用，不阻止 GC。这是 DOM 元素元数据存储的标准解法。

## 排查清单

按这个顺序查，效率最高：

1. 有没有 `setInterval` / `setTimeout` 没清理？
2. 有没有 `addEventListener` 没配对 `removeEventListener`？
3. 有没有订阅（RxJS、EventBus、WebSocket）没退订？
4. 有没有数组/Map 只增不减？
5. 有没有闭包间接持有了大对象？
6. 有没有 Detached DOM 节点？

内存泄漏的本质只有一句话：**不再需要的对象，仍被可达的引用链持有**。找到那条引用链，切断它，问题就解决了。
